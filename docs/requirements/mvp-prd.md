## 变更说明（相对 V1.1）

V1.2 取代 V1.1，成为需求基线。下面点名的结论已经改写进正文。V1.1 里没有被本节改写的决定仍然有效，包括工作区不用 Git Worktree、事件分流、独立验证容器、先 Draft MR 再审核、回灌用尽进入 `WAITING_USER`、Flyway，以及 Git 适配器不把厂商类型写进领域模型。

1. 撤回「MVP 每个项目只关联一个主仓库」和「单项目多仓库不在 MVP」。一个项目关联多个 Git 仓库。一次任务只有一个工作区目录，其中按稳定目录名检出全部关联仓库。Agent 在同一次会话里跨这些检出工作。
2. 统一交付指：一个任务、一个工作区、各仓库同一个分支名 `fp/{taskId}`、只为有改动的仓库各开一条 Draft MR、一次任务级人工审核。它不是把多个远端合并成一个 Git 历史。
3. 控制面继续自建。不把 OpenHands 或其他 Coding Agent 产品分叉进本仓库。MVP 的 Agent 运行时是容器内的 Codex CLI，不实现自研 Java 或 Python Agent 循环。其后只预留 OpenHands Agent Server（REST/WebSocket）和 ACP 适配器。
4. 租户管理员维护本公司的编码工具目录和模型 Provider 目录。项目可设默认工具、Provider 和模型标识，任务可以覆盖这三项。Agent 只拿到这次选定 Provider 的会话级代理地址和短时令牌。Codex 只说 Responses API。只说 Chat Completions 或原生 API 的 Provider 必须标明需要翻译网关，网关未配置前不能给 Codex 使用。
5. 并发任务必须隔离，包括不同需求下同时运行的任务。每个任务有自己的工作区目录、容器、Agent 进程、会话凭证和 Docker 网络。不得共享可写检出、Agent 家目录或会话缓存。bare mirror 只读共享。
6. 个人工作台是登录后的首页。它先按租户、再按项目成员关系和「我的」筛选展示需求与任务，并提供「待我处理」。它按状态打开不同的详情和动作，不是新的业务模块，也不做成 IDE。
7. 租户是公司，也是数据隔离边界。普通用户只属于一个租户。角色为平台管理员、租户管理员、项目管理员、成员。不做计费、公开注册或租户域名产品，也不做跨租户共享。
8. 规约与文档分平台、公司、项目三层。任务启动时合成并冻结进会话。这不是文档库。
9. 操作记录只追加，供审计和日报。不记录工作台页面浏览，也不写入密钥。
10. 任务启动时冻结仓库集合和各仓库基线分支。同一仓库不排他。只有每个需要交付的仓库都已有 Draft MR，任务才进入 `WAITING_APPROVAL`。部分失败时保留已成功的 MR，任务进入 `WAITING_USER` 后只补未完成的仓库。验证命令从工作区根目录执行。工作区和产物有保留策略；操作记录默认长期保留且不可由用户改删。

# 1. 产品概述

## 1.1 产品定位

ForgePilot（云端 AI Coding 平台）以需求为入口，以 AI Agent 为编码执行主体，以平台验证和人工审核为质量门禁，把一次软件修改从需求推进到 Draft MR 和交付记录。

平台负责任务调度、执行环境隔离、证据保存和代码交付。Agent 在授权范围内读取代码、修改代码、执行命令。平台不是通用聊天窗口，也不是在线 IDE。

核心目标：

1. 用户可以创建项目、关联仓库并管理需求。
2. 平台可以把需求拆成可执行的研发任务，拆分结果由用户确认。
3. 平台为每个任务准备独立代码工作区和受限执行环境。
4. AI Agent 可以在授权范围内修改代码。
5. 平台在独立容器中验证 Agent 的结果。
6. 平台凭验证证据和人工审核控制交付，不以 Agent 的自我报告作为完成依据。
7. 需求、任务、代码变更、验证证据和 MR 可以相互追踪。
8. 执行过程可恢复、可审计。执行节点失效后，能依据快照或重新克隆继续处理。

## 1.2 产品核心原则

| 原则 | 说明 |
| --- | --- |
| 需求驱动 | 需求是研发流程的业务入口 |
| 编排与执行分离 | 控制面负责调度和状态，执行面负责运行 Agent |
| 任务与会话分离 | 研发任务不等于 Agent 会话 |
| 执行环境隔离 | 每个任务使用自己的工作区目录、容器、网络和会话凭证；目录内检出项目的全部仓库 |
| 证据驱动 | 完成取决于平台验证、证据和人工审核 |
| 人工可控 | 交付前必须人工审核；等待输入时可以发消息；可以取消或在原工作区重试 |
| 可恢复 | 任务状态、日志、产物和工作区快照持久化 |
| 集成优先 | 使用现有 Git 托管和项目自己的构建命令，不自建 Git 或 CI/CD 引擎 |

## 1.3 MVP 建设目标

MVP 必须打通以下闭环：

创建项目 → 关联多个 Git 仓库 → 创建需求 → AI 分析草稿 + 用户确认 → 拆分任务 + 用户确认 → 为任务建立独立工作区并检出全部仓库 → 在 Docker 沙箱中启动 Agent → 收集 Diff → 平台在新容器中验证 → 失败回灌（默认最多 2 次）或进入等待人工处理 → 平台为有改动的仓库推送同名分支并创建 Draft MR → 一次任务级人工审核 → 完成并生成交付记录。

这条链路能在一个真实的 Java + Vue 项目上稳定运行，即认为 MVP 核心目标达成。试点不依赖 API 文档模块或缺陷模块。

## 1.4 MVP 非目标

第一阶段不建设完整的企业研发管理套件。以下能力明确排除在 MVP 之外：

- Jira / 禅道级别的项目管理系统。
- 缺陷管理，包括轻量缺陷列表。
- Confluence 级别的文档协作，以及项目 Markdown 文档库（上传、版本、检索）。
- API 文档管理和 OpenAPI 的导入、展示、自动生成、差异比对。
- 自研 Git 仓库服务。
- 自研 CI/CD 引擎。平台验证只是执行项目配置的命令。
- 通用可视化工作流设计器，以及任务 DAG 调度器。
- 多 Agent 协作网络。
- 企业知识图谱和代码库级影响分析。
- 计费、公开注册、租户独立域名，以及把一家公司的项目共享给另一家公司。
- 细粒度 API、页面操作和资源归属编辑器。
- Token 消耗看板和资源配额产品。
- Monaco Editor、在线终端、云 IDE，以及进入沙箱的交互式 PTY。
- 把多个 Git 远端合并成一个仓库，或跨远端做一次合并提交。
- 把控制面拆成大量微服务或十几个 Maven 业务模块。
- 自研 Agent 循环，或把另一套 Coding Agent 产品整仓并入。

# 2. 用户、认证与权限

## 2.1 部署与租户

一套控制面服务多家公司。租户是公司，也是数据隔离边界：用户、项目、仓库、需求、任务、工作台、公司自己的模型密钥，以及公司与项目文档都属于租户。

项目是这家公司里的项目团队。项目有多名成员，关联多个仓库，需求和任务在项目里进行。

普通用户在 MVP 只属于一个租户。平台管理员是实例级身份，不挂在某一家公司上。MVP 不允许把一个项目共享给另一个租户。不计费，不做公开注册，也不做按租户分域名的 SaaS 产品。

## 2.2 认证

MVP 使用本地用户名和密码登录，签发 JWT。密码只保存散列值。

GitLab OAuth、其他社交登录和企业单点登录不在 MVP。代码托管凭证与登录身份分开配置，见凭证与集成章节。

## 2.3 角色

MVP 有四种角色：

| 角色 | 职责 |
| --- | --- |
| 平台管理员 | 实例级配置、执行节点、平台层规约与文档，以及跨租户查询操作记录。不因此获得各公司的项目操作权 |
| 租户管理员 | 本公司用户、公司设置、公司层规约与文档、创建项目、本公司模型目录 |
| 项目管理员 | 本项目成员、仓库连接、验证命令、编码工具与 Provider 的项目默认值、项目层规约与文档 |
| 成员 | 在所属项目中使用工作台、需求、任务，以及自己有权做的审核 |

一个用户只属于一个租户，但可以同时是租户管理员和若干项目的成员或项目管理员。项目内不再细分开发、测试等角色。

## 2.4 权限

MVP 权限有三层：

1. 租户边界：公司数据只在本公司内可见。平台级规约与文档例外，所有租户可读。
2. 菜单权限：决定用户能否看到对应导航。
3. 项目成员关系：决定用户能否访问该项目下的需求、任务、日志、Diff、MR 和项目操作记录。

平台管理员可以进入平台管理，并跨租户查询操作记录。项目数据仍然按成员关系访问。排障账号必须被显式加入项目。

以下能力放到后续版本：页面按钮级权限、按接口逐项授权的编辑器、资源归属人权限。

## 2.5 Agent 的执行身份

Agent 不继承当前用户的全部权限。平台为每次执行创建受限的任务执行身份，限制：

- 可访问的项目和仓库。
- 可读写的工作区。
- 可调用的工具。
- 可访问的网络。
- 可执行的 Git 操作。Agent 进程不得 `git push`，不得创建 MR/PR，不得合并受保护分支。

Agent 容器内不得出现 Git 平台长期令牌、模型 Provider API Key、数据库口令、消息队列口令或对象存储管理密钥。访问 Git 和模型时使用第 4.10 节的短时凭证。

# 4. 核心业务模块需求

## 4.1 工作台

工作台是登录后的首页，不是新的业务模块。它读取项目、执行和交付里已有的需求和任务，不另建一套工作台状态。

访问边界先是用户所属租户，再是项目成员关系。用户只看到本公司里自己所属项目的需求和任务。平台管理员不因为管理身份看到未加入的项目。

默认筛选叫「我的」，范围是：

- 用户创建的需求，以及用户担任负责人的需求。
- 用户创建的任务，用户担任负责人的任务，以及上面这些需求下面的任务。

用户可以改成「项目内全部」，看到所属项目里的全部需求和任务。另有「待我处理」：在「我的」范围内，任务处于待审核、等待人工，或会话正在等待输入。打开工作台页面本身不写操作记录。列表同时给出数量：当前筛选下的需求、任务、执行中、验证中、待审核、等待人工处理。可以展示采集到的用量事件条数，但不得呈现为准确的 Token 消耗看板。

从一行打开详情。详情就是这条需求或这个任务，按所处阶段展示不同内容和动作。AI Coding、测试与交付里打开的是同一条记录。

阶段：

- 需求处于待分析或设计中：展示可编辑的 AI 分析草稿和建议任务列表。动作是编辑和确认，不是 IDE，也不是正式审批。
- 任务处于 `RUNNING`：展示会话状态、所选 Provider 和模型标识、本次检出，以及普通文本日志。WebSocket 续传日志，不使用 xterm.js 或 PTY。会话处于 `WAITING_INPUT` 且适配器声明了交互输入时，可以发送一条消息。否则可以取消，或在同一工作区附说明后重试。适配器未声明原生暂停时，不提供暂停后从原进程恢复。
- 任务处于 `VERIFYING`：展示工作区根目录上的验证命令、输出和退出码。
- 任务处于 `WAITING_APPROVAL`：展示该任务全部 Draft MR、轻量 Diff、证据，以及任一仓库中被修改或删除的测试文件。没有改动的仓库要标出来，并且没有 MR。通过则任务完成且不合并；要求修改则在同一工作区开新 Session。
- `WAITING_USER`、节点中断、`FAILED`、`COMPLETED`、`CANCELLED`：展示已有证据。等待人工时可以重试、取消或明确放弃。完成后可以查看交付记录。取消和失败不把任务伪装成仍在运行。

不要求研发效能分析看板。不引入 Monaco Editor。

## 4.2 项目管理

### 4.2.1 项目

支持新建、编辑、归档和搜索。

| 字段 | 说明 |
| --- | --- |
| 项目名称 | 必填 |
| 项目编码 | 唯一 |
| 项目描述 | 说明 |
| 技术栈 | 如 Java、Vue，用于展示和选择默认验证命令模板 |
| 项目状态 | 正常、归档 |
| 默认编码工具 | 可选。指向本公司编码工具目录中的一条。任务可以覆盖 |
| 默认模型 | 可选。指向本公司模型目录中的一条 Provider，并填写模型标识。任务可以覆盖 |
| 关联仓库 | 一条或多条。见 4.2.2 |
| 自动回灌上限 | 默认 2，可按项目修改 |

归档项目不能再启动新的执行。

### 4.2.2 仓库

一个项目关联多个 Git 仓库。仓库连接是一对多，不是项目上的单个主仓库字段。这是 MVP 范围。

每条连接包含：

- 仓库地址。
- 托管类型。已实现 GitLab 与 GitHub。数据模型保留提供商字段，不把厂商专有结构写进项目、需求或任务。github.com 远端自动识别为 GitHub。
- 稳定的本地检出目录名。任务工作区用这个名字作为子目录，不随一次执行改变。目录名在项目内唯一，且不能是路径。
- 可选的基线分支。未填写时由适配器读取远端默认分支。Draft MR 指向这条基线，不使用项目级的统一基线分支。
- 连通性测试、分支列表、最近提交查询。
- 加密保存的集成凭证，按这条连接存放。接口不得把凭证明文返回前端。

平台使用这些凭证访问 Git 托管。Agent 容器不接收长期凭证。GitHub 与 GitLab 是两个适配器，不改任务和需求的领域字段。GitLab 令牌使用 `FORGEPILOT_GITLAB_TOKEN`，GitHub 令牌使用 `FORGEPILOT_GITHUB_TOKEN`。公开 GitHub 仓库可以不带令牌克隆；推送和 Draft PR 缺令牌时必须明确失败。

平台不把多个远端合并成一个 Git 历史。一次任务仍会把这些仓库全部检出到同一个工作区目录里，见第 4.6 节。

任务一旦启动，仓库集合和每条连接当时的基线分支就冻结在该任务上。之后给项目增删仓库或修改基线分支，不改变已经启动的任务。同一仓库可以被多个任务同时检出，平台不加排他锁。各任务使用自己的 `fp/{taskId}`。

### 4.2.3 项目成员

支持添加成员、移除成员、指定该成员在本项目中是否为项目管理员。成员只能访问已加入的项目。

## 4.3 需求管理

需求是业务主线。一个需求可以拆成多个任务。

### 4.3.1 需求字段

| 字段 | 说明 |
| --- | --- |
| 需求名称 | 必填 |
| 需求编码 | 系统生成 |
| 所属项目 | 必填 |
| 需求描述 | Markdown |
| 业务背景 | 可选 |
| 功能范围 | 可选 |
| 验收标准 | 建议必填 |
| 优先级 | 高、中、低 |
| 负责人 | 项目成员 |
| 需求状态 | 见下文 |

需求属于项目。它不单独再选仓库。任务启动时检出的是该项目当时关联的全部仓库。

需求状态：

- 待分析
- 设计中
- 待开发
- 开发中
- 测试中
- 待验收
- 已完成
- 已取消

### 4.3.2 需求状态与任务状态

八个需求状态保留，供人工表达进度。它们必须和任务状态相连，不能各写各的。

规则：

1. 用户可以随时人工修改需求状态。人工修改写入审计。人工标成「已完成」或「已取消」后，自动规则不再覆盖。
2. 自动规则只处理其余状态：
   - 该需求下任一任务处于 `PREPARING`、`RUNNING`、`WAITING_USER`、`VERIFYING` 或 `WAITING_APPROVAL` 时，需求状态改为「开发中」。
   - 该需求下每一个未取消的任务都是 `COMPLETED`，且至少有一个 `COMPLETED` 时，需求状态改为「待验收」。
3. 「测试中」保留给人工标记，MVP 不根据验证容器的启动自动切换。任务级验证状态在任务上查看。
4. 需求「已完成」表示用户验收通过，与单个任务 `COMPLETED` 不是同一件事。

### 4.3.3 需求版本

需求发生重要修改时生成版本快照，记录版本号、正文、验收标准、修改人、修改时间和说明。

Agent 执行绑定确定的需求版本。需求随后发生变化时，不得改写正在执行的任务已经绑定的快照。再次执行时，由用户选择最新版本或原版本。

### 4.3.4 AI 需求分析

用户可以发起 AI 分析。输入是当前需求文本，外加可选的轻量上下文：仓库文件树或 README 摘要。输出是可编辑草稿，不是代码库级影响分析。

草稿建议包含：

1. 需求理解。
2. 根据文本整理的功能范围。
3. 建议的业务流程。
4. 基于文本的技术风险和待澄清问题。
5. 验收建议。
6. 研发任务拆分建议。

MVP 不承诺可靠识别影响模块、数据库变更或 API 变更。草稿里如果出现这类推断，必须标明「未经代码库验证的推测」。在出现能够实际阅读代码的后续分析能力之前，这些推测不能当作正式结论。

AI 不得在未经用户确认时修改正式需求。确认动作记录确认人和时间。这是确认，不是第 4.9 节的正式审核流。

### 4.3.5 任务拆分

一个需求可以包含多个研发任务。用户可以增删改 AI 给出的拆分建议，确认后任务才进入可执行状态。

任务之间可以填写一个可选的前置任务。前置任务未完成时，平台拒绝启动后继任务。MVP 不提供 DAG 编辑器，也不把并行 DAG 编排作为验收项。没有前置关系的任务由用户分别启动。

## 4.4 AI Coding 任务

### 4.4.1 任务模型

任务是调度和执行的业务对象。一个需求有多个任务，一个任务有多个 Agent Session。

任务字段包括：编号、项目、需求、需求版本、名称、描述、类型、优先级、平台分配的工作分支、状态、负责人、Agent 配置、模型 Provider 与模型标识（可空，表示沿用项目或 Agent 默认）、可选前置任务、创建与执行时间。任务不单独绑定一个仓库。基础 SHA 记在每个检出上。

任务类型：代码开发、缺陷修复、重构、测试补充、文档修改、代码审查。这里的「缺陷修复」是任务类型，不代表存在缺陷管理模块。

工作分支名由平台生成，形式为 `fp/{taskId}`。每个有改动的仓库都使用这个名字，各自推到自己的远端。Agent 不得另起分支名。

### 4.4.2 任务状态

状态代码：

- `PENDING`：待执行，含容量不足时在控制面队列中的等待。
- `PREPARING`：已分到执行节点，正在准备 mirror、clone 或容器。
- `RUNNING`：Agent Session 正在执行。
- `WAITING_USER`：等待人工决定。包括 Agent 向用户提问、回灌次数用尽、节点中断后需要人决定是否重试。
- `VERIFYING`：平台正在独立容器中执行验证命令。
- `WAITING_APPROVAL`：Draft MR 已创建，等待人工审核。
- `COMPLETED`：审核通过。
- `FAILED`：明确放弃，或不可恢复的基础设施错误。
- `CANCELLED`：用户取消。

Agent 可以报告会话结果，不能把任务写成 `COMPLETED`。进入 `COMPLETED` 只能由审核通过触发。

`FAILED` 不是验证失败的默认归宿。验证失败且仍可回灌时回到 `RUNNING`；次数用尽后进入 `WAITING_USER`。

### 4.4.3 执行流程

1. 校验任务状态、项目成员关系和仓库配置。
2. 若节点容量已满，任务保持 `PENDING`，记录在 PostgreSQL 队列中。
3. 调度器选定执行节点，任务进入 `PREPARING`。
4. 为该任务准备独立工作区目录，并冻结当时的仓库集合与各仓库基线分支。按冻结结果准备 bare mirror，把每个仓库从自己的基线分支克隆到稳定子目录，记录各自的基础 SHA。
5. 创建只属于该任务的 Agent 容器和网络，注入这次 Provider 的会话级短时凭证和执行策略。家目录放在该任务目录内。
6. 启动 Agent，绑定本次 Session。
7. 转发实时输出，并把重要事件写入控制面。
8. Agent 会话结束后收集 Diff。未提交的改动保留在该任务工作区。
9. 销毁 Agent 容器并撤销会话凭证。工作区保留。
10. 进入平台验证。

每次执行新建 Session。历史 Session 不可覆盖。同一任务默认同时只有一个活动 Session。

### 4.4.4 Session

Session 记录：标识、任务、Agent 类型与版本、模型配置版本、执行节点、工作区、容器标识、起止时间、状态、错误摘要、重要事件序号。Token 用量只有在执行侧确实上报时才记录，缺失时留空，不影响任务状态。

Session 状态：`CREATED`、`STARTING`、`RUNNING`、`WAITING_INPUT`、`SUCCEEDED`、`FAILED`、`INTERRUPTED`、`CANCELLED`。

会话 `FAILED` 只表示这次进程失败，不自动把任务打成 `FAILED`。控制面根据原因决定重试、进入 `WAITING_USER` 或在基础设施不可恢复时把任务标为 `FAILED`。

### 4.4.5 人工操作

支持：

- 启动。
- 取消。取消后清理容器，保留工作区和已收集证据，任务进入 `CANCELLED`。
- 在同一工作区上重新执行，可附带说明。
- 当 Session 处于 `WAITING_INPUT` 时发送一条消息。
- 查看实时日志、工具调用轨迹和 Diff。
- 在 `WAITING_USER` 选择重试、取消或明确放弃。明确放弃进入 `FAILED`。

MVP 的「人工接管」就是以上操作。不提供进入沙箱的交互式终端，也不把接管做成 IDE 会话。

只有 Agent 适配器声明支持原生暂停时，才允许暂停正在运行的进程。未声明时，不要提供「暂停后从原进程恢复」。需要停下来时，取消当前 Session，保留工作区，再开新 Session 并带上说明。

### 4.4.6 任务详情

任务详情从工作台、AI Coding 或测试与交付打开，都是同一条任务。执行中的面板包括：

- 需求与任务上下文，包括绑定的需求版本、所选 Provider 和本次检出。
- 实时日志。使用普通文本，按序号续传。
- 工具调用轨迹。
- Diff 查看。使用轻量 Diff 组件即可。

不包含 Monaco Editor，不包含终端模拟器，不允许用户在沙箱里打开交互式 Shell。动作以第 4.1 节和第 4.4.5 节为准。

## 4.5 Agent 管理

平台通过 Agent Adapter 接入外部 Agent 运行时，不把某一款 CLI 写进领域服务，也不把别的 Coding Agent 产品分叉进本仓库。控制面是 ForgePilot 自己的。MVP 不实现自研的 Java 或 Python Agent 循环。

MVP 的第一个适配器是 OpenAI Codex CLI。平台准备多仓库工作区和 Docker 沙箱，Codex CLI 在 Agent 容器内运行。验证通过后的 `git push` 和 Draft MR 由平台执行。

适配器必须声明能力：交互输入、原生暂停、中断、事件流、工具调用事件、会话恢复、结构化结果。平台只展示该 Agent 声明过的操作。Codex CLI 在 MVP 中声明：支持中断、事件流、工具事件、在工作区内恢复 CLI 自己的会话，以及结构化结果；不声明原生暂停，也不声明把消息送进仍在运行的进程。因此不为 Codex 提供暂停后从原进程恢复，也不在 Codex 会话上提供交互式发消息。需要继续修改时，在同一工作区上开新的 Session。

下一个适配器只留端口，本阶段不实现：OpenHands Agent Server（REST/WebSocket），以及 ACP 兼容 Agent。

配置项包括名称、类型、版本、启动命令与参数、环境变量模板、可选的默认 Provider 与模型标识、工具权限、超时和资源限制。密钥不出现在配置回显中。模型密钥配置在平台侧的目录里，运行时只通过模型代理下发会话级入口。

租户管理员维护编码工具目录和模型目录。解析一次执行时，任务上的工具、Provider 和模型标识优先，其次项目默认，再次工具配置上的默认。三者都引用本公司目录。Codex 任务若选中的上游不是 Responses，且没有配置翻译网关，则拒绝启动。

统一采集并转换成平台事件的内容见第 9 章。判断执行是否结束必须依据会话状态和退出结果，不能只解析终端文本。

## 4.6 工作区与沙箱

### 4.6.1 工作区

每个任务拥有一个工作区目录。执行节点为每条仓库连接维护一份 bare mirror；任务启动时，平台把项目关联的每一个仓库 `git clone` 到工作区下的稳定子目录，目录名来自项目配置。允许使用 `git clone --reference` 引用对应 mirror。mirror 只读共享，可写检出不共享。

```
{node-storage}/
├── mirrors/
│   └── {repositoryId}.git
└── workspaces/
    └── {taskId}/
        ├── .agent-home/
        ├── {localDirectoryNameA}/
        └── {localDirectoryNameB}/
```

不使用 Git Worktree 作为隔离机制。worktree 目录里的 `.git` 文件保存它所指向仓库的绝对路径，容器内除非把该仓库挂到完全相同的路径，否则 Git 不可用。多个 worktree 还共享对象库和锁，一个任务执行 `git gc` 或持有锁时会干扰其他任务。

工作区记录：标识、任务、执行节点、根路径、Agent 家目录、状态、创建时间和最后活动时间。每个检出另记仓库连接、clone 路径、基础 SHA 和平台分支名。

未提交、未推送的改动位于执行节点磁盘。为了在节点失效后还能恢复，平台在执行过程中定期，并在 Session 结束时，把工作区打成快照：

- 每个检出都要做。将该检出中未提交和未跟踪的文件记录到这个仓库自己的隐藏 ref，或据此生成 `git bundle`。只保存其中一个检出，或只保存当前分支 HEAD，都不足以恢复。
- 快照存入 Git 远端和/或 MinIO，并在控制面记录元数据。
- 节点失效后，新节点拉取该快照并恢复；若快照不存在，则重新克隆基础 SHA，并明确告诉用户节点上尚未打快照的本地改动已经丢失。

容器内的非 root 用户必须与宿主机工作区目录的属主使用一致的 UID/GID，或采用等价的固定 UID 策略，使 Agent 能写入挂载目录。

工作区与容器生命周期分离。容器可以销毁，工作区不因此删除。

保留策略可以按平台或租户配置天数。未结束任务的工作区不因到期被删。已结束、且每个检出都已有快照或已经推送的工作区，才允许在到期后清理。操作记录默认长期保留，不设短保留期；只有平台保留作业可以删除过期记录，用户和管理员都不能改、不能删。导出日报不必再存一份快照。

### 4.6.2 Docker 沙箱

MVP 用 Docker 运行执行环境。

- Agent 会话使用一个容器。
- 平台验证使用另一个新容器，挂载同一工作区。验证容器不包含 Agent CLI 和模型凭证。见第 4.8 节。

两类容器都遵守：

- CPU、内存、磁盘和执行时间限制。
- 非 root、非特权。不挂载宿主机 Docker Socket。
- 独立 Docker 网络，出站默认拒绝。
- 允许访问的目标包括该项目全部仓库连接上的 Git 主机、执行节点上的模型代理（仅 Agent 容器需要），以及项目声明的包仓库。
- 禁止访问控制面、PostgreSQL、Redis、RabbitMQ、MinIO 管理接口和云元数据服务。

验证容器默认不接收 Git 写凭证。它只执行项目配置的命令。

### 4.6.3 执行节点

执行节点向控制面注册，上报 `nodeId`、并发容量和标签，并持续心跳。

控制面调度器把 Session 分到具体节点，同时遵守全局并发上限和该节点的并发上限。按项目的并发上限以后再做。没有容量时，任务留在 PostgreSQL 的待执行队列，而不是只堆在 RabbitMQ 里。

节点心跳超时后，该节点上的 Session 标为 `INTERRUPTED`，对应任务进入 `WAITING_USER` 并通知用户。恢复依赖第 4.6.1 节的快照。只有在无法恢复且无法重新从各检出的基础 SHA 开始时，才把任务标为 `FAILED`。

同一节点上同时运行的任务仍然各自使用独立工作区、容器、网络、Agent 进程和会话凭证。调度器的全局并发和单节点并发只限制数量，不放宽隔离。bare mirror 可以按仓库在节点上只读共享。

## 4.7 执行证据

平台不以 Agent 的自我声明作为完成依据。关键结果保存为证据，元数据在 PostgreSQL，文件在 MinIO。

证据类型：

- 会话日志文件。
- 工具调用摘要。
- Git Diff。
- 工作区快照的位置。
- 验证命令、退出码和 stdout/stderr。
- 若验证工作区中存在 JUnit XML，则保存该文件。
- 审核记录。
- MR 地址。

证据记录包含标识、任务、Session、类型、对象存储地址、摘要、生成时间、来源和校验状态。

已完成的日志、Diff、报告和 bundle 都上传到 MinIO。控制面和 Web 只从对象存储读取。运行中的输出尾部由执行服务经控制面转发给浏览器，不把执行节点磁盘暴露给 Web。

## 4.8 平台验证

### 4.8.1 何时执行、在哪里执行

Agent Session 结束并完成 Diff 收集后，任务进入 `VERIFYING`。平台在同一多仓库工作区上启动一个新容器，在工作区根目录执行项目管理员配置的命令，使一条命令可以覆盖多个检出。

验证容器与 Agent 容器分离：里面没有 Agent CLI，没有模型凭证，也没有模型代理所需的会话令牌。这样测试过程不能再调用模型，也不能复用 Agent 的工具权限。

该能力是「按项目配置执行命令」，用于构建和测试。它不解析流水线语言，不调度多阶段 CI，不替代 GitLab CI 或 GitHub Actions。

### 4.8.2 项目配置

项目可以配置：

- 构建命令。
- 测试命令。
- 超时时间。
- 命令所需的非机密环境变量。

MVP 不提供可配置的通用测试报告解析规则。平台保存退出码、标准输出和标准错误。如果命令在约定路径留下 JUnit XML，平台把文件当作产物保存，不做跨框架的报告产品。

### 4.8.3 结果与回灌

验证命令退出码非零，或未能在超时内结束，视为验证未通过。

未超过回灌上限时，平台用新的 Session 把失败信息交回 Agent：失败命令、退出码、错误摘要、相关日志和当前 Diff。默认最多自动回灌 2 次，次数按项目配置。

达到上限后，任务进入 `WAITING_USER`。由用户决定在同一工作区重试、取消，或明确放弃。不得因为次数用尽自动进入 `FAILED`。

审核页面除了展示 Diff 和验证结果，还必须标出测试文件是否被修改或删除，避免只靠删除测试来获得通过的退出码。标出的方式可以是路径规则（如 `src/test`、`*Test.java`、`*.spec.ts`）加上本次 Diff 的文件清单，不要求独立的测试分析产品。

## 4.9 确认与审核

MVP 有两个人工检查点。

### 4.9.1 分析与拆分确认

用户确认 AI 分析草稿和任务拆分后，任务才允许启动。系统记录确认人、时间和所确认的需求版本。不为此建设可转交、可驳回的审批单。

执行前授权、高风险操作审批不进入 MVP 流程。架构上可以留策略挂钩，默认不拦截。

### 4.9.2 代码审核

验证通过后，平台先完成统一交付，任务再进入 `WAITING_APPROVAL`。审核人看到的是该任务的全部 MR 与证据，而不是先在平台内批准、再去创建 MR。

审核是任务级的一次决定，覆盖这些 MR 和共享证据，不是按仓库各做一次互不相关的审批。

审核页展示：需求版本、任务说明、会话摘要、每个有改动仓库的 Diff 和 MR 链接、没有改动因而不创建 MR 的检出、验证退出码与日志、任一仓库中测试文件被修改或删除的提示，以及其他证据。

审核结果：

- 通过：任务变为 `COMPLETED`。平台不合并任何 MR。
- 要求修改：在同一工作区创建新 Session，任务回到 `RUNNING`。已有 Draft MR 保留，后续推送更新同一分支名下各仓库原来的 MR。

审核记录只追加，不覆盖。MVP 不要求转交和独立的「MR 创建审批」。创建 MR 是平台在验证通过后的自动动作，它本身不是一个审批关卡。

## 4.10 Git 集成与凭证

### 4.10.1 Git 操作

通过 Git 适配器完成，领域服务只依赖平台自己的仓库、分支、提交、Diff 和 MR 模型。

适配器实现 GitLab 与 GitHub：读取仓库、分支和提交，查询 Diff，创建分支，创建 Draft 合并请求（GitLab 为 Draft MR，GitHub 为 Draft PR），查询状态。合并不在自动动作中。

`git push` 和 MR/PR 创建由平台执行。执行位置可以在执行服务中、Agent 容器之外。Agent 进程不执行这两步。

### 4.10.2 分支与 MR

验证通过后，平台做一次统一交付。这个词的意思是：一个任务、一个工作区、各仓库使用同一个平台分支名、协调创建 Draft MR、一次人工审核。它不是把多个远端合成一个 Git 仓库，也不是跨远端做一次 merge commit。

1. 平台检查工作区里的每一个检出。相对该检出的基础 SHA 没有需要交付的改动时，不推送，也不创建 MR。
2. 对有改动的每个仓库，平台把该检出推送到 `fp/{taskId}`。分支已存在则更新。各仓库使用同一个分支名，各自推到自己的远端。
3. 对有改动的每个仓库，平台创建或更新指向该仓库默认分支的 Draft MR。
4. 每条 MR 保存仓库连接、外部标识、URL、head SHA 和幂等键。
5. 全部需要创建的 MR 都成功或命中已有记录后，任务进入 `WAITING_APPROVAL`。

幂等范围是任务加仓库。幂等键取任务、仓库和 head SHA，或等价键。同一次推送的重试返回该仓库已有的 MR，不得为同一仓库再建一条。head 前进时更新该仓库原来的 Draft MR。不同仓库各有自己的一条开放 MR。

部分仓库成功、部分失败时，已经成功的 Draft MR 保留，失败仓库记为可重试，任务进入 `WAITING_USER`。用户重试交付时，平台只补这些未完成的仓库，仍用同一个 `fp/{taskId}`，不新开分支，也不撤销已成功的 MR。全部需要的 MR 都创建或命中之后，任务才进入 `WAITING_APPROVAL`。只有 Git 托管或执行节点处于不可恢复故障时，任务才进入 `FAILED`。

Agent 不得合并受保护分支。MVP 不自动合并。

### 4.10.3 凭证代理

Git 长期令牌只保存在平台的加密配置中。

需要在容器内访问 Git 时，通过 `GIT_ASKPASS` 或 git credential helper 提供短时、限定到本项目的令牌。令牌不得写入环境变量，不得写进 remote URL，以免进入进程列表、日志和 `git remote -v`。

Agent 容器内的 Git 凭证不授予推送和创建 MR 的使用权。平台在 Agent 容器之外执行推送时，另行使用短时凭证，并在该次操作结束后失效。

模型调用由执行节点上的模型代理完成。执行服务按第 4.5 节选定的那一条 Provider 签发会话级 base URL 和短时令牌。Agent 容器只拿到这一组入口。Provider 的真实 API Key 只存在于代理侧。代理校验会话令牌后，再以平台保存的 Provider 密钥访问模型服务。并发任务的令牌互不通用。

Codex CLI 当前只说 Responses API。代理对 Agent 暴露的必须是 Responses 兼容接口（`wire_api = "responses"`）。可以直接接到已经提供该接口的上游：OpenAI、Azure OpenAI（自定义 Provider）、Amazon Bedrock、Google Cloud Vertex AI、Ollama、LM Studio，以及任何暴露 Responses 兼容 API 的网关（例如 OpenRouter）。

只提供原生 API 或 `/v1/chat/completions` 的 Provider（包括 Anthropic 原生接口，以及许多只支持 Chat Completions 的厂商）不能直接配给 Codex。执行节点上的模型代理，或放在代理后面的翻译网关（例如 LiteLLM），负责把这些上游转换成 Responses。翻译发生在 Agent 容器之外。目录中要把这类 Provider 标成需要网关；网关未配置时，Codex 任务不能选用它。

Session 结束、取消或判定中断时，撤销本次 Git 会话凭证和模型会话令牌。

## 4.11 交付记录

任务 `COMPLETED` 时生成交付记录，关联：需求版本、任务、相关 Session、Diff、验证证据、审核记录和 MR URL。

交付记录是只读归档。MVP 不附带 API 文档版本或缺陷单。

## 4.12 平台、公司与项目配置

平台管理员管理实例：执行节点、沙箱镜像和资源限制、平台层规约与文档，以及跨租户的操作记录查询。平台管理员不维护各公司的模型密钥。

租户管理员管理本公司：

- 用户：新增、编辑、禁用。普通用户只属于这一家公司。
- 模型目录：名称、类型（适配器标识，不是厂商 SDK 类型）、base URL、密文引用、是否启用、API 版本、上游协议，以及其他非机密参数。只说 Chat Completions 或原生 API 的记录必须能标出需要翻译网关。密钥加密存储，界面和接口都不返回明文。
- 编码工具目录：名称、适配器类型、版本、启动参数、能力声明、可选的默认 Provider 和模型标识。
- 公司层规约与文档。

项目管理员管理本项目的成员、仓库连接、验证命令、默认编码工具、默认 Provider 与模型标识，以及项目层规约与文档。

集成界面文案使用「代码托管」，不把页面做成不可替换的 GitLab 专用控制台。

不提供资源配额产品和 Token 成本看板。若模型代理或平台调用能够得到用量，可以写入可选的用量事件，供以后使用。

## 4.13 规约与文档

规约和文档分三层，更具体的一层补充或覆盖上一层：

1. 平台层：平台管理员维护，所有租户可读。例如平台期望的交付和验证方式。
2. 公司层：租户管理员维护。例如语言、安全、Git、审核和日志规范。
3. 项目层：项目管理员维护。例如模块边界、多个仓库如何配合、验证命令说明。

这不是通用文档库，也不做评论、版本维基或知识库检索。MVP 也不做 API 文档和 OpenAPI 导入。

每条记录有范围、标题、可选分类、正文或文件、是否启用，以及是否进入 Agent 上下文。规约默认进入 Agent。文档默认只给人看；勾选之后才进入 Agent。

项目成员可以阅读平台层、本公司层和本项目层。只有对应层次的管理员能修改该层。公司层和项目层不跨租户。大文件在 MinIO，元数据在 PostgreSQL。

任务启动时，平台按平台、公司、项目的顺序合成启用中且标记进入 Agent 的规约。标题相同视为冲突，更具体的一层覆盖上一层；标题不同的规则全部保留。合成结果的内容和散列写入本次 Session。会话进行中再改规约或文档，不改变已经启动的 Agent。

工作台和项目页要能看到这次会交给 Agent 的有效规约，而不是只展示某一层。

## 4.14 操作记录与日报

操作记录是可查询的一等数据，不只是内部审计表。它只追加。登录和鉴权失败、租户与项目及成员和仓库的变更、规约与文档、编码工具和 Provider 配置、需求及其状态、分析与拆分确认、任务生命周期、会话的启动取消重试和接管消息、验证结果、推送和 MR 的创建或更新、审核通过和要求修改，都要记录。工作台的页面浏览不必逐条记录。

每条记录包含：租户（只有平台级操作可以为空）、操作者（用户或系统或服务身份）、发生时间、动作类型、对象类型和标识、适用时的项目、请求号、给人读的中文摘要、结构化载荷、成败。载荷中的令牌、密码和 Provider 密钥必须打码，明文不得入库。

公司只能查询自己的记录。平台管理员可以跨租户查询。项目成员只能看自己有权访问的项目记录。

记录要能按租户、项目、操作者、时间范围、动作、需求和任务筛选。日报按这些记录生成：当天每个用户、每个项目新建了哪些需求或任务，哪些发生了推进、完成、审核或受阻，再加上当前仍「待我处理」的存量。存量来自任务当前状态，不来自页面浏览。MVP 提供查询和 JSON、CSV 或 Markdown 导出，供人或以后的作业生成日报。不做完整的报表产品，也不把 Token 成本写进日报。定时邮件留到 MVP 之后。

普通用户和租户管理员都不能修改或删除操作记录。只有平台保留作业可以删除超过长期保留期限的记录。默认不自动删除。

# 5. 核心业务流程

## 5.1 需求到交付

1. 用户创建项目并关联一个或多个 Git 仓库。
2. 用户创建需求。
3. 平台生成 AI 分析草稿，用户编辑并确认。
4. 平台按确认结果生成任务，用户调整可选前置关系并确认。
5. 用户启动任务。容量足够时，执行节点为该任务建立独立工作区，检出项目的全部仓库，并启动只属于该任务的 Agent 容器。
6. Agent 修改代码。平台收集日志和 Diff，并周期性写工作区快照。
7. Agent 会话结束。平台销毁 Agent 容器，撤销会话凭证。
8. 平台在新容器中执行验证命令。
9. 验证失败且未超过回灌上限：携带失败证据启动新 Session。
10. 验证失败且达到上限：任务进入 `WAITING_USER`。
11. 验证通过：平台对每个有改动的仓库推送 `fp/{taskId}`，按任务加仓库幂等创建 Draft MR。全部成功或命中已有 MR 后，任务进入 `WAITING_APPROVAL`。部分失败则进入 `WAITING_USER`，已成功的 MR 保留。
12. 审核通过：任务 `COMPLETED`，写入交付记录，不合并。
13. 审核要求修改：同一工作区上启动新 Session。

## 5.2 任务状态迁移

合法迁移：

- `PENDING` → `PREPARING`：调度器分配到有容量的节点。
- `PREPARING` → `RUNNING`：Agent Session 已启动。
- `PREPARING` → `WAITING_USER`：准备工作区失败但可以人工重试。
- `RUNNING` → `WAITING_USER`：Session 处于 `WAITING_INPUT`，或执行中断后需要人工处理。
- `RUNNING` → `VERIFYING`：Agent 会话成功结束，Diff 已收集。
- `RUNNING` → `FAILED`：发生不可恢复的基础设施错误。
- `WAITING_USER` → `RUNNING`：用户重试或回复后继续，使用新 Session 或在 `WAITING_INPUT` 下发送消息。
- `WAITING_USER` → `CANCELLED`：用户取消。
- `WAITING_USER` → `FAILED`：用户明确放弃。
- `VERIFYING` → `RUNNING`：验证失败且未超过回灌上限。
- `VERIFYING` → `WAITING_USER`：验证失败且达到回灌上限，或推送 / 创建 MR 失败但现场保留。
- `VERIFYING` → `WAITING_APPROVAL`：验证通过，且每个有改动的仓库都已推送 `fp/{taskId}`，对应 Draft MR 已按幂等键创建或命中。没有改动的仓库不产生 MR。
- `WAITING_APPROVAL` → `COMPLETED`：审核通过。不自动合并。
- `WAITING_APPROVAL` → `RUNNING`：审核要求修改。
- 允许取消的非终态 → `CANCELLED`。

`VERIFYING` 在回灌次数用尽时不得进入 `FAILED`。

每次迁移记录操作者（或系统）、原因、时间和关联 Session。

## 5.3 Session 状态

`CREATED` → `STARTING` → `RUNNING`。

`RUNNING` 可以进入 `WAITING_INPUT`、`SUCCEEDED`、`FAILED`、`INTERRUPTED` 或 `CANCELLED`。`WAITING_INPUT` 收到用户消息后回到 `RUNNING`。

节点心跳丢失时，该节点上未结束的 Session 标为 `INTERRUPTED`。任务是否失败由第 5.2 节决定，不由 Session 状态直接写成任务 `FAILED`。

# 6. 系统形态

详细结构见 [系统基础架构设计说明书](../architecture/system-architecture.md)。需求侧约定如下。

## 6.1 控制面与执行面

控制面是一个 Spring Boot 3 应用，包为：

- `system`：用户、认证、角色、菜单权限、审计。
- `project`：项目、成员、仓库、需求。
- `execution`：任务、Agent、Session、工作区、沙箱调度、节点和证据的控制面状态。
- `delivery`：验证编排、审核、MR、交付记录。

边界稳定前不把这些包拆成多个 Maven 业务模块。

执行面是独立进程，负责 Docker、clone、Agent 进程、模型代理和产物上传。执行面不裁决任务是否完成。任务状态以控制面数据库为准。

控制面调用执行节点来启动、取消和发起验证。执行节点向控制面推送心跳、事件、结果和产物。两边使用独立于用户 JWT 的服务身份。

## 6.2 技术选型

| 层次 | MVP 技术 |
| --- | --- |
| 前端 | Vue 3 + TypeScript + Vite + Pinia + Vue Router + Element Plus |
| 实时 | WebSocket，按事件序号续传 |
| Diff | 轻量 Diff 查看器 |
| 后端 | Java 17 + Spring Boot 3 + MyBatis-Plus |
| 迁移 | Flyway |
| 数据库 | PostgreSQL |
| 缓存与高频流 | Redis / Redis Stream |
| 控制事件 | PostgreSQL Outbox + RabbitMQ |
| 对象存储 | MinIO |
| 隔离 | Docker |
| 代码托管 | Git 适配器；实现为 GitLab 与 GitHub |

不引入 Monaco Editor 和 xterm.js。向量检索、OpenTelemetry 的完整落地留到后续，MVP 先具备结构化日志、健康检查和基础指标。

## 6.3 部署

MVP 部署 Web、控制面、执行服务、PostgreSQL、Redis、RabbitMQ、MinIO 和至少一个 Docker 执行节点。Git 托管和模型 Provider 在外部。

开发环境可以用 Docker Compose 放在同一台机器上，但控制面和执行面必须是不同进程，权限边界仍然有效。

## 6.4 工作流实现

任务流转用代码中的状态机实现，状态放在 PostgreSQL。不为 MVP 引入通用工作流引擎或 DAG 调度器。

可选前置任务只做「启动前检查」。RabbitMQ 用于投递控制事件，Outbox 保证状态变更和待投递事件同事务写入。

1. 核心业务表使用统一主键，并记录创建人、创建时间、修改人、修改时间。状态历史、事件、操作记录和审核记录只追加。操作记录没有给用户使用的更新或删除。

5. `merge_request` 对幂等键唯一，并且同一任务在同一仓库上至多一条开放 MR。重复创建返回原记录。没有改动的仓库没有 MR 行。

# 8. 接口范围

对外 API 使用 `/api/v1`，并校验 JWT 与项目成员关系。列出的是 MVP 需要覆盖的能力，路径可以在设计时微调，但不得缺少对应行为。

## 8.1 身份与项目

- 登录、当前用户。
- 项目的增删改查、成员维护。
- 仓库连接的增删改查、连通性测试、分支与最近提交。一个项目可以有多条连接。
- 模型目录的维护。响应不得包含长期密钥。
- 项目默认 Provider 与模型标识；启动任务时的覆盖。未指定时按第 4.5 节的顺序解析。

## 8.2 需求与任务

- 需求 CRUD、版本列表、发起分析、确认草稿、确认拆分。
- 任务 CRUD、启动、取消、重试、在 `WAITING_INPUT` 时发送消息。
- 任务的 Session、重要事件、证据和 Diff。Diff 内容来自 MinIO。
- 不提供「暂停 / 恢复」接口，除非将来某适配器声明该能力后再单独增加。

## 8.3 验证、审核与 MR

- 查询验证记录和日志。
- 审核通过、要求修改。
- 查询任务的 MR。
- 不提供由浏览器直接调用 Git 托管令牌的接口。创建 MR 由验证通过后的平台流程触发；若进入 `WAITING_USER` 后需要重试交付，由「重试交付」动作再次触发同一幂等流程。

## 8.4 实时

- WebSocket 推送任务状态、会话输出、工具调用摘要、验证状态和 MR 结果。
- 客户端携带上次收到的序号。服务端从该序号之后补发。高频输出的补发窗口放在 Redis Stream；超出保留期的历史日志改从 MinIO 读取。

## 8.5 执行面内部接口

执行服务调用控制面，使用服务身份：

- 节点注册与心跳。
- 上报事件、结果、产物和验证结果。

控制面调用执行节点，使用服务身份：

- 启动 Agent 会话。
- 取消会话。
- 在指定工作区启动验证容器。
- 在 Agent 容器之外执行推送，并请求创建 MR 所需的 Git 操作。

内部接口校验调用方、任务归属和幂等键。用户 JWT 不能调用这组接口。

# 9. 实时事件与通知

## 9.1 两条事件路径

控制与状态事件使用 PostgreSQL Outbox + RabbitMQ，例如任务状态变化、会话生命周期、审核结论、MR 已创建。消费者按事件 ID 幂等处理。失败消息进入死信队列。事件体不得含长期密钥或短时令牌。

高频流不进入 RabbitMQ，也不逐条写入 `agent_event`。Agent 标准输出、token 和详细工具日志写入 Redis Stream，或由执行服务经控制面的 WebSocket 转发。完整日志异步上传 MinIO。

`agent_event` 只保存重要事件：状态变化、工具调用摘要、文件变更记录、等待输入、会话结束和错误摘要。

## 9.2 通知

MVP 使用站内通知。需要通知的情况：等待输入、等待人工处理、验证未通过且次数用尽、节点中断、等待审核、MR 已创建、任务完成、任务失败。

企业微信、飞书、钉钉和邮件以后再接。

# 10. 安全与恢复

## 10.1 安全

- Agent 与验证容器都非特权、非 root，且有资源上限。
- 长期密钥不进入 Agent 容器，也不出现在 remote URL 和环境变量中。
- 容器出站默认拒绝，允许列表见第 4.6.2 节。
- 会话结束撤销 Git 与模型的短时凭证。
- 工具调用受适配器策略约束。
- 工作区按任务隔离，容器用户对挂载目录可写。
- Agent 不能合并受保护分支，MVP 不自动合并。
- 敏感操作写审计。
- 测试文件被修改或删除时，审核界面必须可见。

## 10.2 恢复

Agent 异常退出时：保存已有日志和 Diff，更新 Session 状态，保留工作区，按策略打快照，再由控制面决定进入回灌、`WAITING_USER` 或 `FAILED`。

执行服务重启时，根据容器实际状态重新上报，不得直接把 PostgreSQL 中的任务标成完成或删除。

执行节点失联时：Session 标为 `INTERRUPTED`，任务进入 `WAITING_USER`，用户得到通知。新节点用隐藏 ref 或 bundle 恢复；没有快照时只能从基础 SHA 重新克隆，并说明丢失范围。

Web 或控制面重启不丢失任务状态，因为权威状态在 PostgreSQL，产物在 MinIO。Redis 中的实时流可以因重启而缺一段，客户端改拉 MinIO 上已经上传的日志。

# 12. MVP 实施顺序

实施时先走通闭环，再考虑第 14 章的后续项。不要并行铺开已排除的模块。

## 第一阶段：基础业务

- Flyway、本地登录和 JWT。
- 用户、四个角色、菜单权限、租户和项目成员。
- 项目，以及每个项目的多条仓库连接。
- 模型目录，以及项目默认 Provider。
- 需求与需求版本。
- 模型配置的加密保存。

验收：用户可以登录，创建项目，连上仓库，创建需求。

## 第二阶段：执行底座

- 任务和可选前置任务。
- 分析草稿、用户确认和任务确认。
- Agent Adapter 与 Codex CLI。
- 执行节点注册、心跳和 PostgreSQL 排队。
- bare mirror、每任务一个多仓库工作区、UID/GID 一致的挂载。
- Agent 容器、模型代理、短时 Git 凭证。
- Session 和经控制面转发的实时日志。

验收：用户确认任务后能启动 Agent，在隔离 clone 中修改代码，并在页面上看到持续输出。

## 第三阶段：证据与恢复

- 重要事件落库，完整日志进 MinIO。
- Diff 收集。
- 工作区快照。
- 取消、重试和节点失联后的 `INTERRUPTED` / `WAITING_USER`。
- WebSocket 按序号续传。

验收：Agent 异常退出或节点失效后，仍能看到历史、日志和已打快照的代码变更，并能在新 Session 中继续。

## 第四阶段：验证

- 项目级验证命令。
- 验证使用新容器。
- 保存退出码和日志，遇到 JUnit XML 则保存文件。
- 失败回灌，默认最多 2 次，用尽后进入 `WAITING_USER`。
- Diff 中标出测试文件的修改和删除。

验收：平台在 Agent 容器之外执行项目命令；失败能回灌；次数用尽后停在人工处理，而不是把任务标为失败。

## 第五阶段：交付

- 平台推送 `fp/{taskId}`。
- 幂等创建 Draft MR。
- 审核通过则完成并写交付记录；要求修改则在原工作区开新 Session。
- 不自动合并。

验收：从一个需求可以追踪到任务、Diff、验证证据、审核和 MR。不包含 API 文档、项目文档和缺陷单。

# 13. MVP 验收标准

## 13.1 业务

- 能创建用户和项目，并用本地账号登录。
- 能为一个项目关联多个 GitLab 或 GitHub 仓库，并为每条连接配置稳定目录名。领域接口不依赖厂商类型。
- 能维护模型 Provider 目录。项目可以设置默认 Provider 和模型标识，任务可以覆盖。没有 Responses 能力且没有翻译网关的 Provider 不能被 Codex 任务选用。
- 两个任务并行时，工作区、容器、Agent 进程和会话凭证彼此独立，即使它们属于不同需求、落在同一执行节点。
- 能创建需求、保存版本，并用人工或自动规则看到与任务一致的需求状态。
- AI 分析以草稿形式出现，未经确认不改正式需求，且不把推测写成代码库级影响结论。
- 能确认任务拆分。前置任务缺失时可以执行；填写了一个前置任务时，前置未完成不能启动。
- 能在独立工作区中启动 Agent。工作区包含项目的各个仓库检出。页面能查看实时输出、工具轨迹和 Diff。
- 能在新容器中执行项目验证命令，看到退出码和日志。
- 验证失败能回灌，默认不超过 2 次；用尽后任务处于等待人工处理。
- 验证通过后能看到平台为有改动仓库创建的 Draft MR，并做一次任务级审核。没有改动的仓库没有 MR。
- 审核通过后任务完成，MR 未被平台合并。
- 能打开交付记录，其中没有 API 文档和缺陷模块依赖。

## 13.2 执行

- 每个 Session 有独立记录，重试不覆盖历史。
- 每个任务有独立工作区目录。一个任务的 Git 操作不使用其他任务的可写检出，也不依赖共享 worktree 锁。同一工作区里的多个 clone 分属不同远端。
- 同一任务不会出现两个活动 Session。
- 容量满时任务留在控制面队列。
- 节点失联后 Session 为 `INTERRUPTED`，用户收到通知，已有快照可以在新节点恢复。
- 取消任务会清理容器并保留已归档证据。
- 控制面重启后任务状态仍可读取。

## 13.3 安全

- Agent 容器中不存在 Provider API Key 和 Git 长期令牌。
- Git 令牌不在环境变量和 remote URL 中。
- 会话结束后短时凭证失效。
- Agent 容器不能访问控制面、数据库、Redis、RabbitMQ、MinIO 管理接口和云元数据地址。
- 验证容器没有 Agent CLI 和模型凭证。
- 容器非特权。
- 项目成员以外的用户不能读取该项目的 Diff、日志和 MR。
- Agent 不能合并受保护分支。
- 审核页能看出测试文件被修改或删除。

## 13.4 试点

以一个真实的 Java + Vue 项目试点，不要求该项目先接入 API 文档或缺陷模块：

1. 创建项目并关联仓库。
2. 创建带验收标准的需求。
3. 生成分析草稿，由用户修改并确认，再确认任务。
4. Agent 修改后端和前端代码。
5. 平台收集 Diff。
6. 平台在新容器中执行构建和测试。
7. 至少演练一次验证失败后的回灌，以及一次达到上限后的人工处理。
8. 验证通过后出现 Draft MR，人工审核后任务完成。
9. 交付记录能串起上述输入、输出和证据。

# 16. 实施约束

开发必须遵守：

1. 先固定领域模型和状态机，再扩展页面。
2. 控制面四个包之间通过服务接口协作，不要跨包直接改对方的表。
3. 不要在控制面进程中启动 Agent。
4. 异步状态以 PostgreSQL 为准，并带幂等。
5. 每次 Agent 执行有唯一 Session，每次代码执行关联一个工作区。
6. 不要用 Agent 文本直接驱动任务状态。
7. 不要把长期凭证传入 Agent 容器。
8. 不要用 Git Worktree 作为任务隔离方案。
9. 不要把 token 流写入 RabbitMQ 或 `agent_event`。
10. 不要在 Agent 容器里跑平台验证。
11. 分支名、推送和 MR 由平台完成。
12. Git 适配器之外的代码不要依赖 GitLab 类型。
13. 页面、接口、数据模型和菜单权限保持一致。
14. 先完成第 13.4 节的试点闭环，再做第 14 章的功能。

架构硬约束的完整列表以 [架构说明书](../architecture/system-architecture.md) 和仓库根目录 `AGENTS.md` 为准。三处不一致时，先改文档再写代码。

# 17. 产品目标

ForgePilot 把需求、Git 托管、构建命令和 AI Agent 组织成一条可追踪的修改链路。平台调度任务，Agent 修改代码，平台验证结果，人工决定是否收下这次修改。

MVP 的目标是让一个真实需求走完这条链路，而不是在第一条链路跑通之前铺开研发管理套件。
