# 需求研发全流程（轻量）

在需求主线上补齐完整但轻量的研发生命周期，用于真实联调。不做工作流设计器、不做外部缺陷系统、不自动合并远端分支。

试点需求：在「九九乘法表验证」项目中，用 HTML + CSS + JS 做一个可在浏览器直接打开的九九乘法表页面（不走构建工具）。仓库使用 `pfyangf/forgepilot-demo99`。

## 1. 环节、门禁与复用

| 顺序 | 环节 | 做法 | 门禁 |
| --- | --- | --- | --- |
| 1 | 提出需求 | 已有：创建需求，状态「待分析」 | — |
| 2 | 需求分析 | 已有：可编辑分析草稿与建议任务 | — |
| 3 | 需求评审 | 新增：通过 / 驳回 + 意见 | 未通过不得进入设计 |
| 4 | 设计文档 | 新增：挂在需求下的 Markdown 设计稿，支持在线编辑与导入 | 评审通过后进入「设计中」 |
| 5 | 设计文档评审 | 新增：通过 / 驳回 + 意见，可多轮 | 未通过不得开工 |
| 6 | AI Coding 绑定 | 已有：项目默认编码工具、Provider、模型 | 未绑定不能启动开发任务 |
| 7 | 仓库绑定 | 已有：项目关联仓库；GitHub 适配器同步补齐 | 未绑定不能启动开发任务 |
| 8 | 开发 | 已有：IMPLEMENT 任务 + Agent Session | 须满足 3、5、6、7 |
| 9 | 代码评审 | 已有：验证通过后 `WAITING_APPROVAL`，通过或要求修改；Draft MR/PR 不自动合并 | — |
| 10 | 测试 | 已有：`verify` 与 TEST 任务；需求可标「测试中」 | — |
| 11 | 缺陷登记 | 新增：轻量缺陷单（标题、描述、严重程度、状态） | — |
| 12 | 缺陷修改 | 已有任务类型 BUGFIX，须关联缺陷 | — |
| 13 | 回归测试 | 缺陷修复后再次 `verify`，或建回归 TEST 任务 | 未关闭缺陷不能验收 |
| 14 | 验收测试 | 新增：需求在「待验收」时明确通过或退回 | 有未关闭缺陷不能验收 |
| 15 | 发布 | 新增：发布记录（版本号、说明）；不自动合并、不强制打 Git 标签 | 须先验收通过 |

## 2. 需求状态

在原有八个状态上增加三个：`待需求评审`、`待设计评审`、`已发布`。

人工可改状态，写入审计。「已完成」「已取消」「已发布」后，自动规则不再覆盖「已取消」；「已发布」只能从「已完成」进入。

自动规则：

- 确认分析后进入「待需求评审」（不再直接「待开发」）。
- 需求评审通过 →「设计中」；驳回 → 回到「待分析」，可改需求后再提交评审。
- 提交设计评审 →「待设计评审」；通过 →「待开发」；驳回 →「设计中」。
- 任一开发/修复任务处于执行相关状态 →「开发中」。
- 存在进行中的 TEST 任务，或用户标为「测试中」→「测试中」。
- 所有未取消任务均为 `COMPLETED`，且没有 `OPEN` / `IN_FIX` 缺陷 →「待验收」。
- 验收通过 →「已完成」。验收退回 →「测试中」或「开发中」（按是否仍有未关闭缺陷）。
- 发布成功 →「已发布」。

启动 `IMPLEMENT` 或 `BUGFIX` 前必须同时满足：最近一次需求评审为通过、存在设计稿且最近一次设计评审为通过、项目已绑定默认编码工具和模型、项目至少有一个仓库。`TEST` / `DOCS` / `REVIEW` 任务不走开工门禁，但 `REVIEW` 不能代替代码审核状态机。

## 3. 数据

新增四张表，不把 GitLab / GitHub 结构写进需求或任务。

`review`：`subject_type` 为 `REQUIREMENT` 或 `DESIGN_DOCUMENT`；`decision` 为 `APPROVED` / `REJECTED`；意见、评审人、时间。允许多轮，以最近一次为准。

`requirement_document`：归属需求，`kind=DESIGN`，Markdown 正文，版本号，是否为当前待审版本。这不是通用文档库，只服务需求设计稿。

`defect`：编码 `DEF-项目编码-序号`，标题、描述、严重程度 `HIGH|MEDIUM|LOW`，状态 `OPEN|IN_FIX|FIXED|VERIFIED|CLOSED|REJECTED`，关联需求，可选关联任务。`BUGFIX` 任务必须带 `defectId`；任务启动后缺陷进入 `IN_FIX`，任务完成且回归验证通过后进入 `VERIFIED`，关闭后才算结单。

`requirement_release`：归属项目，可关联一个或多个已完成需求；版本号、说明、发布人、发布时间。不自动合并 MR/PR，也不把打标签做成强制步骤。

操作记录覆盖：提交/完成评审、设计稿变更、缺陷开闭、验收、发布。密钥仍要脱敏。

## 4. 界面

沿用现有顶栏和可折叠侧栏，不新开一级菜单。需求详情页增加「研发流程」步骤条和当前环节动作：提交需求评审、写/导入设计稿、提交设计评审、绑定检查、登记缺陷、验收、发布。缺陷列表挂在需求详情，不单独做缺陷产品模块。

## 5. 试点需求正文（创建时使用）

- 标题：九九乘法表页面
- 背景：用一条前端页面需求走完整研发链路，验证平台联调，不追求复杂业务。
- 范围：先产出页面设计说明（布局、配色、交互），评审通过后用单页 HTML + CSS + JS 实现；浏览器直接打开即可；不使用构建工具或后端接口。
- 验收标准：
  1. 有通过评审的设计文档。
  2. 页面完整展示 1 到 9 的乘法表，算式与结果正确。
  3. 版式清晰，可在常见桌面浏览器中阅读。
  4. 无需安装依赖或执行构建命令。
- 任务拆分建议（评审与设计通过后再建）：实现页面（IMPLEMENT）、补充或执行测试（TEST）。若测试发现缺陷，再登记缺陷并建 BUGFIX，修复后回归。

旧任务 `TASK-DEMO99-1`（编写打印程序）已取消，不在这条新需求上重用。


## 6. 接口与界面约定

接口在 `/api/v1` 下，需 JWT，并校验项目成员关系。

- `POST /api/v1/requirements/{id}/confirm-analysis`：确认分析后进入「待需求评审」，保存建议任务标题，不再直接改为「待开发」，也不自动创建 IMPLEMENT 任务。
- `POST /api/v1/requirements/{id}/reviews`：需求评审，body 为 `{ decision: APPROVED|REJECTED, comment }`。
- `POST /api/v1/requirements/{id}/documents` 与 `PUT .../documents/{documentId}`、`POST .../documents/import`：保存或导入设计稿，每次保存生成新版本。
- `POST /api/v1/requirements/{id}/documents/{documentId}/submit-review`：提交设计评审。
- `POST /api/v1/requirements/{id}/design-reviews`（或 `.../documents/{documentId}/reviews`）：设计评审。
- `POST /api/v1/requirements/{id}/status`：人工改状态（不可直接改为「已发布」）。
- `POST /api/v1/requirements/{id}/accept`：验收通过或退回。
- `GET|POST /api/v1/requirements/{id}/defects`，以及 `POST /api/v1/defects/{id}/close|reject|verify`。
- `GET|POST /api/v1/projects/{id}/releases`：发布记录。关联的需求必须已验收完成。
- 创建 `BUGFIX` 任务时必须带 `defectId`。启动 `IMPLEMENT` / `BUGFIX` 前校验开工门禁。

需求详情页沿用现有顶栏和可折叠侧栏，增加「研发流程」步骤条和当前环节动作。缺陷列表挂在需求详情，不增加一级菜单。
